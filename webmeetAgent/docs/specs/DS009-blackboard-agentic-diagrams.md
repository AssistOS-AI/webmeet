# DS009 - Blackboard Agentic Diagrams

## Introduction

The WebMeet Blackboard is the authoritative home for widgets, geometry, groups, attached connections, shared semantic focus, and bounded history. Room infrastructure supplies authorization, serialized persistence, and realtime transport but does not duplicate this functional state.

## Core Content

The persisted board contains `boardId`, monotonically increasing `revision`, widgets, history, and `interactionContext`. The public projection contains `boardId`, `revision`, filtered widgets, and `interactionContext`. Revisions order realtime projections. They are never client preconditions: WebMeet uses serialized last-edit-wins writes, does not accept `expectedBoardVersion`, does not emit `version_conflict`, and ignores realtime projections older than the currently applied revision.

`webmeet_event_command` accepts canonical JSON, deterministic `/event <action> [JSON object]`, and natural `/event` or `/robo` text. Natural input creates an isolated `MainAgent` for one bounded round with internal skills disabled and only the `blackboard-event` skill available. Its context contains the instruction, logical content bounds, safe widget semantics and capabilities, transient global widget ordinals, shared focus, and last affected widget ids. It excludes viewport state, room revision, participant-private data, paths, editor URLs, audit identifiers, and transport identifiers.

Every Blackboard interpretation, correction, and semantic-verification call uses provider-native Structured Outputs with one strict JSON Schema generated from the canonical action, widget, property, connection, Poll/Bullets, SCRIPTA, and semantic-error definitions. Follow-up SCRIPTA document-content generation and paragraph reformulation use their own strict content schema through the same transport. Chat Completions transports use `response_format.json_schema`; Responses transports use `text.format`. Nullable transport fields are removed before canonical validation, and dynamic Poll answer entries are converted back to the canonical question-id map. The server never treats Markdown or unconstrained model prose as an executable event. Runtimes that do not yet expose the Achilles structured helper send the same strict `response_format` through the existing prompt API, so they do not silently downgrade to free-form JSON.

The canonical public actions are `create`, `update`, `delete`, `group`, `ungroup`, `clear`, `undo`, `redo`, `show`, `hide`, and declared widget-domain actions. `focus` is internal and UI-only. `add`, `lock`, and `unlock` are invalid. Events never contain server-generated widget ids, event ids, command ids, revisions, participant ids, or provenance. A multi-event result uses `{events:[...]}`; create events may declare a command-local `ref`, which later ordered targets and connection endpoints may resolve. Duplicate and forward references fail the entire command.

Blackboard content, semantic focus, and revisions are shared, but whether the Blackboard surface is open or enlarged is local browser layout state. Selecting the RoboTeam participant card or the Blackboard toolbar button toggles that surface only for the current participant, exactly like focusing any other participant card. `show` and `hide` return a requester-local visibility result and are never published as room realtime state. Peers continue to receive `blackboard.updated` invalidations while hidden and render the current projection only when they choose to open their own RoboTeam card. SCRIPTA and `/robo` mutations never force another participant's Blackboard surface open.

One command is validated and applied on one working board, persisted only when every event succeeds, recorded as one history entry, and undone as one unit. The server generates ids, resolves references, attaches provenance, updates shared focus, increments revision once, saves, and publishes `blackboard.updated`. RoboTeam mutations use `agent_robo_team` as technical author and retain the authorized participant only as private provenance. UI mutations use the authorized participant and `source: "ui"`; caller-supplied authorship is rejected.

Visible widget geometry defines logical content bounds. An empty board uses `0,0,1200,800`; generated layouts use a default 40-pixel gap and never depend on browser viewport, zoom, or scrolling. Free lines store endpoints. Attached line widgets store `properties.connection.from/to`, where each endpoint identifies a widget and one of `left`, `right`, `top`, `bottom`, or `center`. The renderer derives endpoints from current target geometry, so connections follow moves and resize; deleting either endpoint removes dependent connections.

Semantic context exposes each widget's current canonical rotation. “Rotate by N degrees” adds N to that value, while “rotate to N degrees” sets an absolute value. Rotation preserves the widget center and does not rewrite free-line endpoints merely to achieve a rendered rotation.

Widgets share a non-nested, server-generated `groupId`. Participants form groups with modifier-click or a canvas marquee. Once grouped, clicking or dragging anywhere inside the common bounding box, including empty space between members, selects or moves one strict block. Member editing and individual resize remain unavailable until `ungroup`. The group projection owns one contextual menu with Move, Rotate, Export, Delete, and Ungroup, while resize is exposed only through the eight handles on the group outline. Export is a local visual snapshot and offers transparent PNG or PNG with the solid board theme background. It includes every visible group widget plus attached connections whose endpoints are both group members, uses 16 px padding and 2x output (bounded to 8192 px per side and 32 megapixels), and excludes selection UI, menus, handles, Robo ordinals, fullscreen controls, admin actions, and edit controls. Visual resources are embedded before rendering, and the locally vendored html2canvas renderer runs without SVG `foreignObject` so the output canvas remains origin-clean. Export never calls the network adapter and does not create history or increment revision. Canonical group mutations target `{type:"group",groupId}`: translation moves every member by one delta, rotation moves member centers around the common center and increments their rotations, and resize maps member geometry into an authoritative target bounding box. Resize handles scale axes independently, while Shift preserves the group aspect ratio. Geometry and free-line endpoints scale, but fonts, strokes, and internal controls do not. Minimum widget dimensions still apply. Group deletion atomically removes every member and dependent connection; ungroup preserves final geometry. Group operations increment revision once, create one history command, and undo as one unit. Attached connections may join a group only with both endpoint widgets. Shape text uses `properties.label` and is centered in the shape SVG rather than represented by a second text widget.

Validated chat and toolbar uploads create editable `image` widgets backed by Explorer media assets. The chat composer exposes attachments through a left-aligned plus control whose WebSkel menu currently contains one declarative `Add image` action; stable menu and input-shell structure remains in the component HTML, while presenter actions own its open state and file-picker command. The widget stores only safe source metadata, intrinsic dimensions, alt text, style, and Blackboard geometry; move, resize, rotate, grouping, deletion, history, and focus therefore use the normal canonical event path. Chat publication creates the attachment and widget atomically after Explorer accepts the staged bytes. After that mutation succeeds, the uploader's browser opens and focuses its local Blackboard surface when necessary and immediately applies the returned projection; this local layout transition is not published to peers. Selecting a chat thumbnail likewise opens the current participant's local Blackboard surface and selects the corresponding widget without changing peers' layouts. Contextual insertion of an image into SCRIPTA reuses its asset. Contextual or `/robo` insertion of a group uses the existing origin-clean browser renderer, commits the resulting PNG, and invokes the canonical SCRIPTA media mutation.

`interactionContext` stores `focusedWidgetId`, `lastAffectedWidgetIds`, `updatedBy`, and `updatedAt`. The latest create, manual selection, move, resize, or edit updates global focus; plural follow-up language uses the last affected ids. Missing focused widgets are cleared. Focus changes do not create undo steps.

The interpreter returns either `{events:[...]}` or `{error:{code,message}}`. Ambiguous or unsafe intent returns a precise natural-language error in the instruction language and executes no events. The audit entry transitions directly from `pending` to `success` or `error`; no clarification state or popup exists.

As soon as the chat composer starts with `/robo`, the local browser shows deterministic global ordinal badges over semantic targets, allowing references such as “line 3”. Each ungrouped widget consumes one ordinal. Each rigid group consumes one ordinal displayed as `G<number>` over the group bounds, while its member widgets display no separate ordinals. The safe interpreter context exposes these targets through `board.widgets` and `board.groups`; a group ordinal or a focused member of that group must resolve to `{type:"group",groupId}` so movement, resize, rotation, deletion, and ungroup apply atomically to the entire block. Browser push-to-talk inserts the prefix on microphone press, before the first speech result, so ordinals are visible while the participant formulates the command. Interim speech text remains a local composer projection; release submits the finalized `/robo` text through the same command path as keyboard input. The badges remain active during execution, disappear when the prefix is removed or the command reaches a terminal result, and are transient DOM overlays that never become widget properties or history. A realtime-only `blackboard.command_status` event lets all participants see who is editing after submission. Terminal success remains visible for four seconds, terminal errors for ten seconds, and stale active status expires after the interpreter timeout plus fifteen seconds.

The selected-group overlay is a browser-only projection expanded by eight logical pixels on every side of the current member bounds. Its border and resize handles therefore remain visually separated from member content. Resize previews reapply the same gap while the canonical transform continues to use the unpadded group bounds, so selection spacing never changes persisted geometry, export bounds, or undo history.

## Decisions & Questions

### Question #1: Why is revision not an optimistic concurrency precondition?

Response:
The room mutation lock already supplies a deterministic server order. Revision is required only to discard stale realtime projections; making it a client precondition would reject valid last-edit-wins collaboration and require unnecessary read/retry cycles.

### Question #2: Why is focus shared board state?

Response:
Follow-up commands such as “move it” and “align them” must resolve identically for every participant. Persisting focus and last affected targets on the board provides that deterministic semantic context without relying on participant viewport or DOM selection.

## Conclusion

Blackboard commands remain deterministic and secure while server order defines last-edit-wins behavior, canonical event lists execute atomically, ambiguous instructions fail without mutation, and collaboration status stays transient.
