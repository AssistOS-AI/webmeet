# DS004 - LiveKit Media Runtime

## Introduction

This specification is the local WebMeet authority for the LiveKit media runtime from the application-agent perspective. It folds the durable requirements from the root WebMeet architecture notes into the `webmeetAgent` DS set and aligns them with the current consolidated `webmeetInfra/liveKitServerAgent` topology.

`webmeetAgent` owns WebMeet room state, token issuance, guest invite behavior, recording commands, AI artifacts, and the Explorer WebMeet plugin. It does not proxy live microphone, camera, or screen-share packets. Live media is routed by the LiveKit server supervised by `liveKitServerAgent`.

## Core Content

WebMeet has separate runtime planes:

| Plane | Handles | Owning component |
| --- | --- | --- |
| Control plane | Workspaces, rooms, members, chat, transcript, artifacts, AI jobs, recording commands, LiveKit participant tokens. | `webmeetAgent` through Ploinky MCP tools and scoped HTTP services. |
| Media plane | Live microphone, camera, screen share, data-channel delivery, WebRTC negotiation, RTP/RTCP forwarding. | LiveKit Server supervised by `liveKitServerAgent`. |
| Recording plane | Room composite capture, rendering, MP4 encoding, file writes. | LiveKit Egress supervised by `liveKitServerAgent`. |
| LiveKit runtime state | LiveKit node/room state, message bus behavior, egress coordination. | Redis supervised by `liveKitServerAgent`. |
| TURN/STUN | ICE relay and STUN behavior. | Coturn supervised by `liveKitServerAgent`. |
| Production TLS | Browser-facing WSS/HTTPS signaling proxy and certificate renewal. | Nginx and Certbot supervised by `liveKitServerAgent` in `prod`. |

`liveKitServerAgent` starts Redis, Coturn, LiveKit Server, LiveKit Egress, and then, in `prod`, Nginx and the Certbot renewal loop. Only after required services are ready does it open the TCP health endpoint on `WEBMEET_INFRA_HEALTH_PORT` so Ploinky can mark the dependency ready.

Runtime config for LiveKit, Egress, Redis, Coturn, and production Nginx is generated by `webmeetInfra/liveKitServerAgent/scripts/hooks/preinstall.sh` under `.ploinky/agents/liveKitServerAgent/`. Checked-in YAML files must not be treated as runtime truth. Generated config must use shared derived credentials so `webmeetAgent`, LiveKit Server, and Egress agree on the same LiveKit API key and secret.

Two LiveKit URLs matter:

| Env var | Used by | Contract |
| --- | --- | --- |
| `WEBMEET_PUBLIC_LIVEKIT_URL` | Browser LiveKit client | Browser-reachable `ws://` or `wss://` signaling URL. Public deployments should use `wss://`; local default/dev installs may seed this to the detected workstation IPv4 address so Firefox can form usable ICE pairs with Podman-published media ports. |
| `WEBMEET_LIVEKIT_URL` | `webmeetAgent` server-side Twirp API calls | Internal LiveKit HTTP API URL. Default is `http://liveKitServerAgent:7880`, dev is `http://liveKitServerAgent:17880`, and prod host-network topology is `http://host.containers.internal:7880`. |

`WEBMEET_EGRESS_URL` may appear in recording metadata, but recording control calls use `WEBMEET_LIVEKIT_URL` and LiveKit's `/twirp/livekit.Egress/*` API. Egress itself uses `WEBMEET_LIVEKIT_INTERNAL_WS_URL`, normally loopback inside the consolidated `liveKitServerAgent` container.
`WEBMEET_LOCAL_PUBLIC_HOST` is an optional default/dev operator override for the browser-facing local host address detected by preinstall hooks.

When a WebMeet user joins a room:

1. The browser calls `webmeet_meeting_join` or the guest join API through Ploinky.
2. `webmeetAgent` updates durable presence and returns `livekitUrl`, `roomName`, `participantToken`, and optional RTC config.
3. The browser opens a LiveKit WebSocket signaling connection using the participant JWT.
4. LiveKit validates the JWT against the shared API key/secret and checks room grants.
   The participant JWT must include `video.canUpdateOwnMetadata=true` so clients can
   publish their own participant attributes/metadata updates (for example the local
   projected avatar payload).
5. The browser and LiveKit negotiate WebRTC transport through ICE.
6. Media starts only when the user enables microphone, camera, or screen share.

LiveKit is an SFU. It terminates each browser's WebRTC connection, receives RTP/RTCP packets for published audio/video/screen tracks, tracks subscriber interest, forwards selected encoded streams, handles congestion feedback and retransmission, and re-encrypts media for each receiver. It normally forwards browser-encoded media rather than transcoding room media. The egress worker is the component that subscribes to a room, renders/composites, encodes MP4, and writes recording files.

Media is encrypted in transit on the browser-to-LiveKit and LiveKit-to-browser WebRTC hops. End-to-end media encryption is not configured in this codebase, so LiveKit is trusted infrastructure that can access the encoded media/data-channel payloads needed for SFU routing.

ICE configuration sent in join payloads is kept small enough that Firefox does not emit the five-or-more STUN/TURN warning:

- The default STUN set is at most one URL. A single public STUN URL is included for non-loopback deployments; loopback deployments omit public STUN unless an operator explicitly sets `WEBMEET_STUN_URLS`.
- TURN may contribute at most two URLs by default when a TURN host and credentials are configured: one UDP and one TCP.
- Default and dev local deployments should prefer a detected workstation IPv4 browser URL and TURN host over loopback. This is required for Firefox on macOS/Podman, which can fail ICE when LiveKit advertises only loopback candidates.
- Loopback deployments omit public STUN by default but keep generated TURN entries when TURN credentials are configured. Explicit `WEBMEET_TURN_URLS` remains the custom TURN override.
- The total default ICE URL count is at most three for non-loopback deployments and at most two for loopback fallback.
- `WEBMEET_STUN_URLS` is optional, non-secret, manifest-declared, comma-separated, trimmed, deduped, and deterministic. An empty value disables STUN. When unset, the profile-aware code default applies.
- `WEBMEET_TURN_URLS` remains the explicit TURN override.
- When no useful ICE server entries remain (no STUN URLs and no TURN with credentials), the join payload omits `rtcConfig` entirely so browsers fall back to their default ICE behavior.
- Diagnostics may report ICE URL counts and categories (STUN/TURN/TURNS presence, `iceTransportPolicy`, elapsed connect time) but must not log TURN credentials, LiveKit tokens, SDP, ICE candidates, API keys, or authorization values.

The WebMeet browser client must create LiveKit rooms with the current no-surprise media options:

- `adaptiveStream: false`
- `dynacast: false`
- `autoSubscribe: true` at connect time
- explicit subscription sweeps after connect and publication events
- optional `rtcConfig` built from session ICE servers

Adaptive stream and dynacast remain disabled because the modal creates and attaches media elements after room events; remote video and screen-share downtracks must be negotiated immediately after subscription. Remote video recovery may detach a stale element and toggle the LiveKit publication subscription, but recovery must be bounded per publication and must not create endless subscription loops.

Screen sharing is a browser media flow. The browser prompts for a screen/window/tab, the LiveKit client publishes a `ScreenShare` track with `simulcast: false`, LiveKit forwards subscribed packets, and Egress subscribes to that track only when recording is active. Camera and screen share may be active at the same time as separate LiveKit video tracks.

Microphone processing happens before publish in the browser. `enhanced` mode uses browser audio constraints, a high-pass filter, locally bundled `@jitsi/rnnoise-wasm@0.2.1` sync build for `AudioWorklet`, optional hum notch, compressor/limiter, and gain before publishing a processed track. `standard` uses browser echo cancellation/noise suppression plus requested graph steps. `off` disables browser voice cleanup except explicitly requested graph steps. LiveKit does not run room-wide denoise for human participants in this deployment. Scribe/STT processing belongs to `webmeetStt` and the optional AI worker path.

The RNNoise vendor copy must remain local to `IDE-plugins/webmeet-tool-button/vendor/rnnoise` with package metadata, license, and `THIRD_PARTY_NOTICES.md`. Runtime CDN fetches for RNNoise are not allowed.

Diagnostics must be opt-in through an explicit debug flag such as `WEBMEET_MEDIA_DEBUG` or `webmeetMediaDebug=1`. Diagnostics may summarize room, track, publication, candidate, and media-element state, but must not log tokens, SDP blobs, ICE credentials, API keys, authorization values, raw LiveKit payloads, screenshots, or hidden prompts.

Redis is runtime infrastructure state for LiveKit and Egress. It may contain short-lived LiveKit room, participant, node, routing, and egress coordination data. Because the supervised Redis process runs `redis-server --save 60 1`, Redis may snapshot runtime state under `.ploinky/data/webmeet/redis`. That snapshot remains infrastructure state, not durable WebMeet application data.

Recording starts and stops through WebMeet tools:

1. Browser calls `webmeet_recording_start` or `webmeet_recording_stop`.
2. `webmeetAgent` checks admin access and calls LiveKit Egress APIs with a short-lived server JWT.
3. LiveKit coordinates the Egress job through the LiveKit/Redis control plane.
4. Egress subscribes to room media, composites/renders, encodes MP4, and writes `/data/recordings/<meetingId>/<recordingId>.mp4`.
5. `webmeetAgent` persists recording metadata and creates an artifact entry.

Profile topology is:

| Profile | LiveKit topology | Browser URL | `webmeetAgent` server URL | Egress internal URL |
| --- | --- | --- | --- | --- |
| `default` | Bridge alias `liveKitServerAgent`, default ports. | `ws://<detected-local-ip>:7880` seeded by preinstall, with `ws://127.0.0.1:7880` only as a fallback. | `http://liveKitServerAgent:7880` | `ws://127.0.0.1:7880` inside the infra container. |
| `dev` | Bridge alias `liveKitServerAgent`, alternate ports. | `ws://<detected-local-ip>:17880` seeded by preinstall, with `ws://127.0.0.1:17880` only as a fallback. | `http://liveKitServerAgent:17880` | `ws://127.0.0.1:17880` inside the infra container. |
| `prod` | Host-network `liveKitServerAgent`. | `wss://livekit-skills.axiologic.dev` by profile default. | `http://host.containers.internal:7880` from bridge-resident `webmeetAgent`. | `ws://127.0.0.1:7880` inside the infra container. |

Production host networking is the preferred path for LiveKit media because bridge-mode UDP source-NAT can break the SFU downlink. The Nginx TLS terminator proxies HTTPS/WebSocket signaling to LiveKit `7880/tcp`; it is not the WebRTC media relay. Public media must reach LiveKit host candidates directly on the declared UDP media range, with TCP/TURN fallback available. Cloudflare Tunnel may carry Explorer application traffic and LiveKit signaling in some deployments, but it is not a general public UDP media proxy.

Security boundaries are separate:

| Boundary | Protection | Limit |
| --- | --- | --- |
| Browser to WebMeet tools | Ploinky router auth and secure MCP/HTTP invocation. | Protects application tools, not direct LiveKit media sockets. |
| Guest invite HTTP service | Scoped `/public-services/webmeet/*` guest route plus stored guest token. | Does not grant Explorer or generic MCP access. |
| LiveKit participant access | Room-scoped LiveKit JWT signed by `WEBMEET_LIVEKIT_API_SECRET`. | Token holders can use grants until expiry. |
| LiveKit API/signaling | Server-side API key/secret, TLS for public signaling. | Signaling port is also an API surface and must not be exposed without controls. |
| Redis | Loopback or bridge-local runtime service. | Not product data and must not be publicly exposed. |
| TURN/STUN | Coturn credentials and relay port range. | Relay traffic can become a bandwidth bottleneck. |
| Durable meeting data | AES-256-GCM payloads with wrapped DEKs. | Metadata outside encrypted payloads remains visible; recordings are file artifacts. |

The current deployment is one LiveKit server, one Redis instance, one Coturn process, one Egress worker, and optional production Nginx/Certbot. It is suitable for small rooms and has known pressure points: LiveKit outbound bandwidth, LiveKit CPU, narrow UDP media ranges, browser decode/render capacity, Egress CPU during recordings, recording storage, TURN relay bandwidth, Redis latency under high churn, and `webmeetAgent` file writes during chat or AI bursts.

Operational checks after startup or deployment should include `ploinky status`, container status, and `node /code/server/validate-runtime.mjs` from the WebMeet container. If rooms list but media does not connect, verify that `webmeet_meeting_join` returns a non-empty participant token, `livekitUrl` is reachable from the browser, the profile's LiveKit media ports are reachable, browser candidate stats select the expected transport, and TURN configuration is present when relay behavior is required.

## Decisions & Questions

### Question #1: Why is direct UDP required for preferred production media?

Response:
WebRTC prefers UDP because real-time media should keep moving rather than waiting for late packets. LiveKit signaling can succeed while media fails if public UDP media candidates are not reachable. `WEBMEET_LIVEKIT_FORCE_TCP=true` is a rollback knob, but the preferred production path is direct UDP media to LiveKit plus TCP/TURN fallback.

### Question #2: Why does Egress live inside `liveKitServerAgent` now?

Response:
The current infrastructure image supervises LiveKit Server and Egress in one container with shared loopback access to generated config and Redis. That reduces Ploinky dependency complexity and makes the health gate represent the complete media runtime rather than only one split service.

### Question #3: Why disable adaptive stream and dynacast?

Response:
The current WebMeet modal renders media elements after LiveKit room events. Immediate subscription and downtrack negotiation are more important than SDK visibility optimization, especially for screen share. Future UI changes may re-evaluate this with browser tests that inspect decoded frames.

## Conclusion

WebMeet media remains reliable while `webmeetAgent` keeps application commands and persisted records in the control plane, `liveKitServerAgent` owns the media and recording runtime, Redis remains transient infrastructure state, and public deployments expose signaling and media according to WebRTC requirements.
