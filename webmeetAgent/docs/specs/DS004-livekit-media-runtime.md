# DS004 - LiveKit Media Runtime

## Introduction

This specification is the local WebMeet authority for the LiveKit media runtime from the application-agent perspective. It folds the durable requirements from the root WebMeet architecture notes into the `webmeetAgent` DS set and aligns them with the split `liveKitServerAgent`, `turnServerAgent`, and Web Publishing topology.

`webmeetAgent` owns WebMeet room state, token issuance, guest invite behavior, resource metadata, AI dispatch metadata, and the Explorer WebMeet plugin. It does not proxy live microphone, camera, or screen-share packets. Live media is routed by the LiveKit server supervised by `liveKitServerAgent`.

## Core Content

WebMeet has separate runtime planes:

| Plane | Handles | Owning component |
| --- | --- | --- |
| Control plane | Rooms, members, chat, resources, AI dispatch metadata, and LiveKit participant tokens. | `webmeetAgent` through Ploinky MCP tools. |
| Media plane | Live microphone, camera, screen share, data-channel delivery, WebRTC negotiation, RTP/RTCP forwarding. | LiveKit Server supervised by `liveKitServerAgent`. |
| LiveKit runtime state | LiveKit node/room state, message bus behavior, and routing coordination. | Redis supervised by `liveKitServerAgent`. |
| TURN | ICE relay behavior. | Coturn supervised by the separate `webmeetInfra/turnServerAgent`, enabled alongside `liveKitServerAgent`. |
| Public signaling edge | Browser-facing WSS signaling, exact-path `/rtc` proxying, and the explicit trusted-TLS contract. | `basic/web-publishing`; certificates terminate at the configured `cloudflare` or `external` edge. |

`liveKitServerAgent` starts Redis and LiveKit Server; Coturn is started separately by the peer `webmeetInfra/turnServerAgent`. Each agent exposes an in-container readiness script to Ploinky. `webmeetAgent` depends on both agents without `no-wait`, and Explorer depends on `webmeetAgent` without `no-wait`, so router readiness is reached only after both media dependencies have passed their bounded readiness checks. There is no published WebMeet health port.

Runtime config for LiveKit and Redis is generated by `webmeetInfra/liveKitServerAgent/scripts/hooks/preinstall.sh` under `.data/liveKitServerAgent/generated/`. The TURN preinstall hook validates topology and TLS, then atomically materializes the shared secret as `.ploinky/data/webmeetSecrets/turn/auth-secret`: the host parent is mode `0700`, the mounted leaf is mode `0444`, and Ploinky mounts its directory read-only for Coturn's fixed non-root UID. At process start, `turnServerAgent` reads that bounded startup input and generates the complete secret-bearing Coturn config with mode `0600` inside its ephemeral container `/tmp`; that config disappears with the container. Checked-in YAML files must not be treated as runtime truth. Generated config must use launcher-resolved shared-generated credentials so `webmeetAgent` and LiveKit Server agree on the same LiveKit API key and secret, while LiveKit and Coturn agree on the independent TURN REST authentication secret.

Two LiveKit URLs matter:

| Env var | Used by | Contract |
| --- | --- | --- |
| `WEBMEET_PUBLIC_LIVEKIT_URL` | Browser LiveKit client | Required provider output. Web Publishing emits local `ws://127.0.0.1:8081` or public `wss://meet.<base-domain>` signaling; `webmeetAgent` declares no default and performs no host detection. |
| `WEBMEET_LIVEKIT_URL` | `webmeetAgent` server-side Twirp API calls | Required provider output. Web Publishing emits the private bridge-network upstream `http://livekitserveragent:7880`; `webmeetAgent` never falls back from the browser URL to this internal address or vice versa. |

Web Publishing is the sole topology owner. Its explicit `WEB_PUBLISHING_TLS_EDGE`, `WEB_PUBLISHING_LIVEKIT_MEDIA_IP`, and `WEB_PUBLISHING_TURN_EXTERNAL_IP` inputs determine the trusted signaling edge and separately reachable media/TURN endpoints. `webmeetAgent` has no preinstall hook and declares no LiveKit URL defaults or TURN/STUN topology variables.

When a WebMeet user joins a room:

1. The browser calls the room-first MCP join flow through Ploinky: `webmeet_room_join` for authenticated users, or the same room-scoped invocation for public guest room entry.
2. `webmeetAgent` updates durable presence and returns `livekitUrl`, `roomName`, `participantToken`, and optional RTC config.
3. The browser opens a LiveKit WebSocket signaling connection using the participant JWT.
4. LiveKit validates the JWT against the shared API key/secret and checks room grants.
   The participant JWT must include `video.canUpdateOwnMetadata=true` so clients can
   publish their own participant attributes/metadata updates (for example the local
   projected avatar payload).
5. The browser and LiveKit negotiate WebRTC transport through ICE.
6. Media starts only when the user enables microphone, camera, or screen share.

LiveKit is an SFU. It terminates each browser's WebRTC connection, receives RTP/RTCP packets for published audio/video/screen tracks, tracks subscriber interest, forwards selected encoded streams, handles congestion feedback and retransmission, and re-encrypts media for each receiver. It normally forwards browser-encoded media rather than transcoding room media.

Media is encrypted in transit on the browser-to-LiveKit and LiveKit-to-browser WebRTC hops. End-to-end media encryption is not configured in this codebase, so LiveKit is trusted infrastructure that can access the encoded media/data-channel payloads needed for SFU routing.

ICE configuration sent in join payloads conveys policy only, never server URLs or credentials:

- The join response may include an `rtcConfig` object containing at most one key, `iceTransportPolicy`, set to `'relay'` only when an operator explicitly sets `WEBMEET_ICE_TRANSPORT_POLICY=relay`. The valid default `'all'` policy omits `rtcConfig`; a missing or unrecognized value is a configuration error and fails startup/store creation rather than silently changing ICE behavior.
- `rtcConfig` must never contain an `iceServers` key. `webmeetAgent` does not build STUN or TURN server URLs, usernames, or credentials; that responsibility belongs to `webmeetInfra`: LiveKit's `rtc.turn_servers` configuration mints expiring credentials from the shared secret, and the separate `turnServerAgent` runs Coturn and validates them.
- The `webmeetAgent` manifest and process do not declare or consume STUN URLs, TURN host/port/realm/URLs, relay ranges, static TURN users, or TURN credentials. Only `WEBMEET_ICE_TRANSPORT_POLICY` affects its RTC output.
- The browser-side `buildRtcConfigForSession` mirrors this contract: it forwards `iceTransportPolicy` only when the value is exactly `'relay'` or `'all'`, rejects any present malformed policy/config payload, and never forwards an `iceServers` key even if a legacy-shaped server response somehow still contained one.
- Diagnostics may report `iceTransportPolicy` and elapsed connect time but must not log TURN credentials, TURN/STUN URLs, LiveKit tokens, SDP, ICE candidates, API keys, or authorization values.

The WebMeet browser client must create LiveKit rooms with the current no-surprise media options:

- `adaptiveStream: false`
- `dynacast: false`
- `autoSubscribe: true` at connect time
- explicit subscription sweeps after connect and publication events
- optional `rtcConfig` conveying only an ICE transport policy (never ICE server URLs or credentials)

Adaptive stream and dynacast remain disabled because the modal creates and attaches media elements after room events; remote video and screen-share downtracks must be negotiated immediately after subscription. Remote video recovery may detach a stale element and toggle the LiveKit publication subscription, but recovery must be bounded per publication and must not create endless subscription loops.

Screen sharing is a browser media flow. The browser prompts for a screen/window/tab, the LiveKit client publishes a `ScreenShare` track with `simulcast: false`, and LiveKit forwards subscribed packets. Camera and screen share may be active at the same time as separate LiveKit video tracks.

Microphone processing happens before publish in the browser. Users without saved preferences default to `auto`: WebMeet prefers the locally bundled RNNoise `AudioWorklet`, measures aggregate RMS/peak/noise/hum values without recording raw audio, detects sustained 50/60 Hz hum, applies conservative adaptive gain before final peak compression, and falls back to standard browser echo cancellation/noise suppression/AGC when the enhanced graph is unavailable. `custom`, `enhanced`, `standard`, and `off` remain explicit manual modes. If a user changes gain, hum filtering, echo cancellation, noise suppression, or AGC while `auto` is selected, the settings draft must switch to `custom` rather than disabling the control. Existing saved settings are not migrated or overwritten. Browser AGC must remain disabled while the local adaptive controller is active to avoid double gain processing.

Remote participant normalization measures each attached remote audio track through a monitoring-only `AnalyserNode` while playback continues through the original media element so output-device routing remains available. Deafen/mute, explicit participant overrides, automatic normalization, and global output volume apply in that order. A manual participant volume adjustment disables automatic normalization for that participant until reset. Monitoring contexts and timers must be disposed on track detach, participant departure, room disconnect, and dashboard destruction.

The RNNoise vendor copy must remain local to `IDE-plugins/webmeet-tool-button/vendor/rnnoise` with package metadata, license, and `THIRD_PARTY_NOTICES.md`. Runtime CDN fetches for RNNoise are not allowed.

Diagnostics must be opt-in through an explicit debug flag such as `WEBMEET_MEDIA_DEBUG` or `webmeetMediaDebug=1`. Diagnostics may summarize room, track, publication, candidate, media-element state, connection quality, and rounded aggregate audio/WebRTC metrics such as RMS, peak, noise floor, adaptive gain, jitter, packet loss, concealed samples, and RTT. They must not log or persist raw audio samples, tokens, SDP blobs, ICE credentials, API keys, authorization values, private-key material, raw LiveKit payloads, screenshots, or hidden prompts. Redaction applies by both field name and content; sensitive aliases, serialized or recursively percent-encoded assignments and keys, URL userinfo, TURN/STUN URLs, complete SDP, ICE candidate lines, and PEM private keys must fail closed without removing unrelated aggregate context. Percent-encoded detection must decode to convergence under a strict pass and work bound; reaching either bound redacts the whole string or key-owned value rather than logging an incompletely decoded value.

All automatic audio processing is self-hosted and browser-local. The runtime may use Web Audio API, WebRTC processing, the vendored Apache-2.0 RNNoise bundle, and self-hosted LiveKit. Paid/cloud denoise services and per-minute audio processing dependencies are outside this contract.

Redis is runtime infrastructure state for LiveKit. It may contain short-lived LiveKit room, participant, node, and routing data. Because the supervised Redis process runs `redis-server --save 60 1`, Redis may snapshot runtime state under `.ploinky/data/webmeet/redis`. That snapshot remains infrastructure state, not durable WebMeet application data.

Profile topology is:

| Profile | LiveKit topology | Browser URL | `webmeetAgent` server URL |
| --- | --- | --- | --- |
| `default` | `liveKitServerAgent`, `webmeetAgent`, and `web-publishing` share only `webmeet-signaling`; Ploinky derives `livekitserveragent` from the canonical agent id, and media ports remain explicit in the infra manifest. | `ws://127.0.0.1:8081`, provided by the local Web Publishing signaling proxy. | `http://livekitserveragent:7880` |
| `dev` | Same as `default` (dev no longer shifts to an alternate port range). | Same as `default`. | `http://livekitserveragent:7880` |
| `prod` | Same `webmeet-signaling` trust zone as `default`; host networking and manifest-declared aliases are forbidden. See `webmeetInfra/docs/specs/DS002-livekit-server-agent.md` for the full rationale. | `wss://meet.<baseDomain>`, a `basic/web-publishing`-owned hostname whose nginx proxies only the exact `/rtc` path to `http://livekitserveragent:7880` — not a direct connection to LiveKit. | `http://livekitserveragent:7880` |

TURN relay now lives in a dedicated `turnServerAgent`, not embedded in `liveKitServerAgent`. Those two infra agents share only `webmeet-turn`, while `webmeetAgent` and Web Publishing are not attached to that zone. Ploinky derives `turnserveragent` from the canonical agent id; aliases are not declared in manifests. LiveKit configures `rtc.turn_servers` with the same `WEBMEET_TURN_AUTH_SECRET` so it can advertise the relay and mint expiring browser credentials that Coturn validates. Web Publishing proxies only the exact `/rtc` signaling path to the explicitly declared trusted TLS edge; it is not the WebRTC media relay. Public media must reach LiveKit's published UDP/TCP media ports directly, with TURN/UDP and TURN/TLS relay through `turnServerAgent` when direct connectivity is unavailable or relay-only policy is selected. Cloudflare Tunnel may carry Explorer application traffic and LiveKit signaling in some deployments, but it is not a general public UDP media proxy, and TURN traffic must never be routed through it.

Security boundaries are separate:

| Boundary | Protection | Limit |
| --- | --- | --- |
| Browser to WebMeet tools | Ploinky router auth and secure MCP/HTTP invocation. | Protects application tools, not direct LiveKit media sockets. |
| Guest invite HTTP service | Scoped `/<webmeetAgent>/roomLoader.html?roomId=<roomId>*` guest route plus roomId-scoped guest session. | Does not grant Explorer or generic MCP access. |
| LiveKit participant access | Room-scoped LiveKit JWT signed by `WEBMEET_LIVEKIT_API_SECRET`. | Token holders can use grants until expiry. |
| LiveKit API/signaling | Server-side API key/secret, TLS for public signaling. | Signaling port is also an API surface and must not be exposed without controls. |
| Redis | Loopback or bridge-local runtime service. | Not product data and must not be publicly exposed. |
| TURN | Coturn auth enforcement and relay limits are owned by `turnServerAgent`; expiring client credentials are minted by LiveKit from their shared secret. | Relay traffic can become a bandwidth bottleneck. |
| Durable meeting data | AES-256-GCM payloads with wrapped DEKs. | Metadata outside encrypted payloads remains visible. |

The current deployment is one LiveKit server, one Redis instance, one Coturn process, and one Web Publishing signaling edge. It is suitable for small rooms and has known pressure points: LiveKit outbound bandwidth, LiveKit CPU, bounded UDP media ranges, browser decode/render capacity, TURN relay bandwidth and quotas, Redis latency under high churn, and `webmeetAgent` file writes during chat or AI bursts.

Operational checks after startup or deployment should include `ploinky status`, container status, `webmeet_room_list`, and a `webmeet_room_join` response with a non-empty participant token. If rooms list but media does not connect, verify that `livekitUrl` is reachable from the browser, the profile's LiveKit media ports are reachable, browser candidate stats select the expected transport, and TURN configuration is present when relay behavior is required.

## Decisions & Questions

### Question #1: Why is direct UDP required for preferred production media?

Response:
WebRTC prefers UDP because real-time media should keep moving rather than waiting for late packets. LiveKit signaling can succeed while media fails if public UDP media candidates are not reachable. `WEBMEET_LIVEKIT_FORCE_TCP=true` is a rollback knob, but the preferred production path is direct UDP media to LiveKit plus TCP/TURN fallback.

### Question #2: Why disable adaptive stream and dynacast?

Response:
The current WebMeet modal renders media elements after LiveKit room events. Immediate subscription and downtrack negotiation are more important than SDK visibility optimization, especially for screen share. Future UI changes may re-evaluate this with browser tests that inspect decoded frames.

### Question #3: Why do media diagnostics redact by content as well as by field name?

Response:
Browser and LiveKit errors can place serialized credentials, recursively encoded assignments, URL userinfo, private-key material, SDP, or ICE candidates under generic keys such as `message` or `detail`. A field-name-only filter therefore leaves straightforward bypasses. Percent decoding continues to convergence under strict work limits, and an input that exhausts those limits is redacted as a unit instead of being logged partially decoded. Separately structured aggregate fields remain available for debugging connection timing and media health.

## Conclusion

WebMeet media remains reliable while `webmeetAgent` keeps application commands and persisted records in the control plane, `liveKitServerAgent` owns the media runtime, Redis remains transient infrastructure state, and public deployments expose signaling and media according to WebRTC requirements.
